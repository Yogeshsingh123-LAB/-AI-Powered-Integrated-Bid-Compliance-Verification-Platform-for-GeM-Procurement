# Deploy BidVerify

Deploy the FastAPI backend on Render and the Vite frontend on a static host, using
Supabase PostgreSQL and a private Supabase Storage bucket. Hosting does not
turn the demonstration GeM/government connectors into authorized live APIs.

## 1. Prepare Supabase

- Reuse your project, or create a new one.
- Copy its **session pooler** PostgreSQL connection string from **Connect**.
  Use `postgresql+psycopg://` as the scheme. Provider `postgres://` and
  `postgresql://` strings are normalized automatically. URL-encode special
  characters in the database password and use `sslmode=require`.
- Create a **private** Storage bucket named `bid-documents`.
- Copy the project URL and a backend **secret** (`sb_secret_...`) or legacy
  **service_role** key from Project Settings → API Keys. An anon/publishable
  key or a database password is not the backend Storage credential.

Put local settings in `backend/.env` using `backend/.env.example`. Do not commit
this file. Check cloud connectivity without changing any data:

```powershell
.\backend\venv\Scripts\python.exe backend/check_deployment.py
```

Both the database and private bucket checks must pass before testing uploads.
`403 Unauthorized` from Storage means the configured credentials/project access
must be corrected. A successful database check does not verify Storage access.

## 2. Prepare administrator credentials

For a **new database**, set `INITIAL_ADMIN_EMAIL` and a strong
`INITIAL_ADMIN_PASSWORD`. Startup creates the first administrator once.
It never resets existing passwords, promotes existing bidders, or reactivates
suspended accounts.

For an **existing database**, production startup rejects an administrator still
using a known demo password. Change that password using the authenticated
`/api/auth/change-password` endpoint, or run the explicit maintenance command:

```powershell
.\backend\venv\Scripts\python.exe backend/manage_admin.py --email admin@gem.gov.in
```

Enter the new password at the hidden prompts. Do not put passwords in command
arguments, source code, screenshots or chat. If an old JWT secret was exposed,
replace `JWT_SECRET` as well to invalidate existing tokens.

## 3. Deploy the backend

Push the changes to a GitHub repository you own. In Render, create a Blueprint
from the repository's `render.yaml`, or create a Docker Web Service manually:

| Setting | Value |
| --- | --- |
| Root directory | `backend` |
| Runtime | Docker |
| Dockerfile | `./Dockerfile` |
| Docker context | `.` |
| Health check | `/health` |

The Dockerfile installs OCR binaries, Indic language data and the English spaCy
model. Its startup command binds to Render's `PORT`, with 8000 as the local
default. Do not use `--reload` in production.

Set these **backend-only** environment variables:

| Variable | Value |
| --- | --- |
| `ENVIRONMENT` | `production` |
| `DATABASE_URL` | Supabase PostgreSQL URI |
| `JWT_SECRET` | Unique random secret of at least 32 characters; generated by the Blueprint |
| `INITIAL_ADMIN_EMAIL` | Initial administrator email |
| `INITIAL_ADMIN_PASSWORD` | Strong non-default initial password for a new database |
| `SUPABASE_URL` | Project URL |
| `SUPABASE_SECRET_KEY` | Backend secret/service-role key from the same project |
| `SUPABASE_BUCKET` | `bid-documents` |
| `CORS_ORIGINS` | Exact frontend production origin, e.g. `https://bidverify.example.com` |
| `GEM_USE_MOCK` | `true` for the SIH demonstration |
| `ENABLE_REAL_API_LOOKUP` | `false` until approved registry access is configured |

Optional AI settings: `AI_PROVIDER=groq`, `GROQ_API_KEY`, or `GEMINI_API_KEY` for
Gemini extraction. Without an extraction key the existing rule-based fallback
remains in use. Never put backend secrets in `VITE_*` variables.

Startup initializes the schema and connects to PostgreSQL. Errors stop startup
instead of silently falling back to a different database. `/health` checks the
database and returns 503 if it cannot be reached.

Choose the hosting plan in your account; the Blueprint does not select a paid
plan for you. OCR/NLP may need more memory than a small free instance provides.
Cloud documents persist in Supabase; the backend's local analysis scratch files
and in-memory demo monitoring data are not durable storage.

## 4. Deploy the frontend

For optional separate frontend hosting, configure your static host with:

| Setting | Value |
| --- | --- |
| Root directory | `frontend` |
| Framework | Vite |
| Node | 24.x |
| Install | `npm ci --include=dev` |
| Build | `npm run build` |
| Output | `dist` |
| `VITE_API_URL` | Public HTTPS Render origin, with no `/api` suffix |

The shared API client sends all API calls to `VITE_API_URL`. WebSockets connect
directly to that backend over `wss`. Redeploy the frontend whenever
`VITE_API_URL` changes because Vite embeds it at build time.

Once your host provides the production URL, put that exact origin in Render's
`CORS_ORIGINS` and redeploy the backend. Separate multiple allowed origins with
commas. Add your custom domain there if you use one.

## 5. Local development and Docker

For Vite development, leave `VITE_API_URL` empty to use the development proxy
to port 8000. The proxy supports HTTP and WebSockets.

```powershell
# Terminal 1, from repository root:
cd backend
.\venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000

# Terminal 2, from repository root:
cd frontend
npm ci --include=dev
npm run dev
```

For Docker Compose, fill in the root `.env.example` as `.env`, including
`POSTGRES_PASSWORD`, `JWT_SECRET`, administrator and Supabase Storage settings.
Compose starts its own PostgreSQL database; it does not use the Supabase
`DATABASE_URL`. Use a strong alphanumeric `POSTGRES_PASSWORD` here to avoid URI
encoding issues in the interpolated database URL.

```powershell
docker compose up --build
```

The frontend at port 3000 uses Nginx to proxy `/api` (including WebSockets) to
the backend. If hosting that frontend container separately, set its
`BACKEND_UPSTREAM` to a reachable backend origin.

## 6. Verify before sharing

Check the configured Supabase database and private bucket from the repository
root. If the bucket does not exist, the setup command creates it privately.
The upload check creates a synthetic PDF, verifies download and signed access,
then deletes that test object:

```powershell
.\backend\venv\Scripts\python.exe backend/setup_storage.py
.\backend\venv\Scripts\python.exe backend/check_deployment.py
.\backend\venv\Scripts\python.exe backend/check_storage_upload.py
```

```powershell
.\backend\venv\Scripts\python.exe -m unittest discover -s backend/tests -v
.\backend\venv\Scripts\python.exe -m pip check
cd frontend
npm test
npm run lint
npm run build
```

API regression tests use a disposable SQLite database and an in-memory storage
test double. They process a real digital PDF but do not validate the hosted
Supabase upload operation, external AI responses, or Linux OCR installation.

After deploying, test actual admin and bidder login, tender creation, a sample
document upload/download, extracted fields, and an officer decision. Check the
browser's Network panel for errors and confirm no requests target localhost.
Keep demo documents separate from real procurement records. Some existing
analytics, mobile, benchmark and government integration screens still contain
demonstration data; these are not proof of live government verification.
